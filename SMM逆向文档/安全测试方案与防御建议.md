# SMM 面板安全测试方案与防御建议

> 基于逆向成果（`REVERSE_FINDINGS.md` + 前端源码 `appsrc/index.js`）做**逻辑分析**，只提供测试方案与修复建议，**不包含任何实际攻击测试**。本文档供面板开发方内部自测使用。

---

## 一、背景与攻击面

逆向确认的核心安全问题：**登录认证只校验 `tgUserId`，不校验 Telegram 签名（initData hash）**。即攻击者无需掌握 Telegram 账号，只要拿到/猜到别人的 `tgUserId`，就可能冒用身份。

从前端源码提取的完整接口面（标注风险等级）：

| 接口 | 功能 | 风险 |
|------|------|------|
| `POST /user/publishTelegramAuth` | 登录换 token（只认 tgUserId） | 🔴 认证绕过 |
| `POST /user/balance` | 查余额 | 🟠 越权读取 |
| `POST /user/sendSmsCode` | 发短信验证码 | 🔴 短信轰炸 / 验证码绕过 |
| `POST /publish/sendTask` | 创建刷量任务 | 🟠 参数篡改 |
| `POST /publish/searchTaskRecord` | 任务记录 | 🟠 越权读取 |
| `POST /publish/searchTaskStatistic` | 任务统计 | 🟠 越权读取 |
| `POST /publish/history/flow` | 历史流水 | 🟠 越权读取 |
| `POST /publish/save/withdraw/account` | 保存提现账户 | 🔴 越权改账户 |
| `POST /publish/recharge/withdraw/flow` | 充值/提现流水 | 🟠 越权读取 |
| `POST /payment/init` | 支付初始化 | 🔴 金额篡改 |
| `POST /usdtPay/createOrderByLegal` | 创建 USDT 订单 | 🔴 金额篡改 |
| `POST /usdtPay/cancelOrder` | 取消订单 | 🟠 状态篡改 |
| `POST /withdraw/init` | 提现初始化 | 🔴 金额篡改 |
| `GET /withdraw/feeRate` | 提现费率 | 🟡 信息泄露 |
| `POST /activity/searchBonusPage` / `searchBonusFlowPage` | 奖金页/流水 | 🟠 越权读取 |
| `GET /publish/checkTaskPublishTime` | 校验视频可发布时段 | 🟡 |
| `POST /dataBoard/search*` | 数据看板 | 🟠 越权读取 |
| `POST /execute/insertTrackEvent` | 埋点 | 🟡 |

## 二、越权测试方案

### 2.1 认证绕过

**前置**：准备两个真实账号 A、B（或已知 B 的 tgUserId）。

| # | 操作 | 预期（安全） | 风险 |
|---|------|-------------|------|
| 1 | 用**任意不存在的 tgUserId** 调 `publishTelegramAuth` | 拒绝，不返回 token | 若能拿到 token → 可伪造任意身份 |
| 2 | 用账号 A 的登录态，把请求头 `tgUserId` 改成 B 的 `tgUserId`，调 `publishTelegramAuth` | 返回的 token 应仍绑定 A（或拒绝） | 若直接拿到 B 的 token → 身份冒用 |
| 3 | 不传 `Authorization`，只传 `tgUserId` 等头，直接调 `balance` | 拒绝（401/10004） | 若通过 → 完全未鉴权 |

**关键验证点**：后端是「从 token 反查用户」，还是「直接信任请求头里的 tgUserId」？若信任请求头，则整个认证形同虚设。

### 2.2 水平越权（IDOR）

用账号 A 的 token，尝试访问/操作 B 的数据：

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | A 调 `balance`，请求头 `tgUserId` 改成 B | 只返回 A 的余额，或报错 |
| 2 | A 调 `searchTaskRecord`，改 `tgUserId` 或 body 里传 B 的 taskId/关键词 | 只返回 A 的任务 |
| 3 | A 调 `publish/save/withdraw/account`，尝试改 B 的提现账户（改 tgUserId 或传 account id） | 只能改自己的账户 |
| 4 | A 调 `publish/recharge/withdraw/flow`、`searchBonusPage`、`dataBoard/search*`，改身份参数 | 只返回自己的数据 |

**重点**：所有「改 tgUserId / Identifier / 传他人 taskId / accountId」的尝试，若后端用这些客户端可控值去查库而不绑定 token 身份，即存在水平越权。

### 2.3 垂直越权

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | 把请求头 `userType` 从 `publisher` 改为 `admin` / `manager` 等，遍历已知接口 | 无任何额外权限 |
| 2 | 探测是否存在管理端接口（如任务审核、提现审核、用户管理），用 publisher token 尝试调用 | 拒绝 |
| 3 | `userEnv`、`userFlag` 等返回字段是否影响权限分支，篡改后能否进入管理逻辑 | 无提权 |

## 三、参数篡改测试方案

### 3.1 金额 / 成本篡改

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | `sendTask` 的 `perUser` 传 `0` / `0.01` / 负数 | 拒绝（服务端校验 ≥2） |
| 2 | `sendTask` 的 `totalUser` 传超大值（如 999999999） | 拒绝或按真实规则计费 |
| 3 | `sendTask` 里夹带 `cost` / `taskCost` / `refund` 字段（前端源码里出现过这些回显字段），尝试指定成本/退款 | 这些字段服务端计算，客户端传入被忽略 |
| 4 | 直接调 `balance` 的写接口（如有），或重放/伪造「增加余额」的请求 | 余额只能由合法流水变动 |

### 3.2 任务参数篡改

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | `sendTask` 的 `type` 改为其他值（如免费/低价服务类型），观察扣费 | 服务端按 type 权威定价，不信任客户端 |
| 2 | `youtubeLink` 传非 YouTube 链接 / 内网地址 / 超长字符串 | 过滤或拒绝（防 SSRF / 注入） |
| 3 | `keyWords` 传 SQL/脚本注入 payload | 无注入 |
| 4 | `endTime` 传过去的时间 / 异常格式 | 校验合法性 |

### 3.3 充值 / 提现（高危，重点）

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | `payment/init` / `usdtPay/createOrderByLegal` 的**充值金额**改为极小值，回调/下单却按大额入账 | 金额服务端生成并签名，客户端不可改 |
| 2 | 伪造充值成功回调（如模拟第三方回调通知） | 回调有签名校验 + 幂等 |
| 3 | `withdraw/init` 的**提现金额**改为大于余额 | 拒绝 |
| 4 | 提现金额改负数 / 极小值反复提现 | 拒绝 / 有频率限制 |
| 5 | `usdtPay/cancelOrder` 取消已支付订单 | 已支付订单不可取消或需审核 |
| 6 | `publish/save/withdraw/account` 保存的提现账户被注入/伪造 | 账户格式校验 |

### 3.4 短信验证码

| # | 操作 | 预期（安全） |
|---|------|-------------|
| 1 | 高频调 `user/sendSmsCode`（同一手机号） | 有频率限制（防轰炸） |
| 2 | 绕过验证码：验证码校验接口是否可跳过/爆破 | 验证码服务端校验、有次数限制与过期 |
| 3 | 验证码能否复用 / 是否绑定业务上下文 | 一次性、绑定操作 |

## 四、防御建议

### 4.1 认证加固（最优先）

- **校验 Telegram 签名**：`publishTelegramAuth` 必须校验 `initData` 的 `hash`（用 Bot Token 按 Telegram 规范验证），确认请求来自 Telegram 官方。
- **服务端解析身份，不信任客户端**：`tgUserId` / `userType` / `Identifier` 一律从签名或 token 在服务端反查，**忽略客户端请求头里传的这些值**。
- token 加过期时间、绑定设备/会话，避免被长期复用。

### 4.2 越权防护

- 所有数据查询/操作以 **token 绑定的用户 ID** 为唯一身份依据，数据库查询强制带上 `WHERE user_id = 当前用户`。
- 管理接口做角色鉴权（admin/普通用户分离），并做接口级权限校验。

### 4.3 参数校验

- **金额字段（perUser、cost、taskCost、refund、充值/提现金额）全部服务端计算/校验**，不接受客户端传入。
- 服务类型 `type` 的定价表服务端维护，客户端只传「服务 ID」。
- 输入过滤：`youtubeLink`、`keyWords`、账户字段做格式校验与转义，防 SSRF/注入/XSS。

### 4.4 资金安全（充值/提现）

- 充值回调：第三方回调通知做**签名校验 + 幂等键**（防重复入账）。
- 提现：金额服务端校验（≤ 可用余额）、加二次验证（短信验证码）、加频率/风控限制。
- 订单状态机服务端权威控制，客户端只能发起「下单/取消」请求，不能篡改「支付成功」等关键状态。

### 4.5 其他

- 短信验证码：加频率限制、图形验证码、验证码有效期与一次性消费。
- 对 `checkTaskPublishTime`、`dataBoard/*` 等读接口统一走鉴权与越权防护。

## 附：测试建议

1. 用两个真实账号做交叉越权测试（2.1/2.2），最可能快速命中「信任客户端 tgUserId」的问题。
2. 资金接口（3.3）建议用测试环境 + 测试金额验证，避免影响生产账本。
3. 优先级：**4.1 认证加固 > 3.3 资金安全 > 2.2 水平越权 > 3.1 金额篡改**。
