## 二、确认的漏洞

### 2.1 认证绕过（严重）

**现象**：`POST /user/publishTelegramAuth` 的请求体只有 `{tgUserId, tgFirstName, tgLastName, userName}`，**不含 Telegram 签名（initData hash）**，后端只认 `tgUserId`。

**实测**：
- 用不存在的 `tgUserId=1111111111` 调登录 → 返回 `{code:0, success:true, data:null}`（拿不到 token，但接口不拒绝）
- 用真实 `tgUserId=8196195827`（本人）调登录 → 正常返回 token（此前已验证，名字都可不填）

**结论**：后端**不校验 Telegram 签名**，只按 `tgUserId` 发 token。攻击者只要拿到任意真实用户的 `tgUserId`（可通过 `@userinfobot` 等公开方式获取），即可调用登录接口换取该用户的 token，**完成身份冒用**。

### 2.2 水平越权 / 身份信任缺陷（严重）

**现象**：所有接口的请求头里 `tgUserId` / `Identifier` 是客户端可控的，后端**信任请求头的 tgUserId 作为身份依据**，而不是从 token 反查。

**实测**（用本人 token `hpFpBg/...`）：

| 操作 | 返回 | 说明 |
|------|------|------|
| 正常（token + 本人 tgUserId）查 balance | `2993.00` | 本人余额，token 有效 |
| 改 `tgUserId=9999999999` 查 balance | `0.00` | **查到了别的账号的余额**（该 tgUserId 余额为 0） |
| 改 `Identifier=XXX999`（tgUserId 不变）查 balance | `2993.00` | Identifier 不影响身份 |
| 改 `tgUserId=9999999999` 查 searchTaskRecord | `total:0` | 查到了别的账号的任务列表（为空） |

**结论**：改请求头的 `tgUserId` 就能查对应账号的余额、任务记录等数据。结合 2.1 的认证绕过，**攻击链完整**：拿目标 tgUserId → 换 token → 以目标身份读取（甚至可能操作）其数据。

## 三、未发现漏洞的部分（安全）

### 3.1 垂直越权（userType 提权）

- 改请求头 `userType=admin` 调接口，返回与 `userType=publisher` **完全相同**（balance 仍为本人 2993）。
- 说明 `userType` 头不参与权限判断（或后端忽略该字段），**无法通过改 userType 提权**。

### 3.2 publisher 访问 admin 后台

- 前端源码中发现独立 admin 后台域名 `https://admin.teenpattiokay.com`。
- 用 publisher token 访问其所有接口（dataBoard/*、balance、searchTaskRecord 等）均返回 **HTTP 401**。
- 说明 admin 后台有独立鉴权，publisher token 被正确拒绝，**无法越权访问 admin 数据**。

## 四、admin 权限结构（源码还原）

前端源码（`appsrc/index.js`）中暴露的 admin 后台信息：

- **Admin 域名**：`https://admin.teenpattiokay.com`（常量 `JT`）
- **暴露的接口**（数据看板 `dataBoard`，共 4 个）：

| 接口 | 功能 |
|------|------|
| `POST /dataBoard/searchChannelDailyUpdateView` | 频道每日更新视图 |
| `POST /dataBoard/searchVideoPlayNum` | 视频播放量 |
| `POST /dataBoard/searchVideoContentView` | 视频内容视图 |
| `POST /dataBoard/searchVideoTimeView` | 视频时长视图 |

- **认证**：admin 后台独立鉴权，publisher token 一律 401 拒绝（实测）。
- **前端关系**：publisher 端的「YoutubeData」页硬编码了 admin 域名并调用上述 dataBoard 接口，但请求会被 401 拒绝（前端仅 console 报错，不展示数据）。

> 说明：admin 后台的其余管理接口（用户管理、任务审核、提现审核等）**未在前端源码中暴露**，本次仅发现上述 4 个 dataBoard 接口。

## 五、完整攻击链（供修复参考）

```
1. 获取目标用户 tgUserId（@userinfobot / Telegram 公开信息）
2. POST /user/publishTelegramAuth { tgUserId: 目标ID }  → 拿到目标 token
3. 用目标 token + 目标 tgUserId 调任意接口 → 读取/操作目标数据
```

核心根因：**认证不校验 Telegram 签名 + 后端信任客户端可控的 tgUserId 头**。两者叠加，导致身份可完全伪造。

---

## 六、修复建议（按优先级）

1. **校验 Telegram 签名（最高优先）**：`publishTelegramAuth` 必须校验 `initData` 的 `hash`（按 Telegram 官方规范，用 Bot Token 验证），确保请求真实来自 Telegram 且 `tgUserId` 未被篡改。
2. **服务端反查身份**：所有接口的身份以 **token 反查出的用户 ID** 为准，**忽略客户端请求头里的 `tgUserId` / `Identifier` / `userType`**。
3. 数据库查询强制绑定 `WHERE user_id = 当前用户`，杜绝水平越权。
4. token 加过期时间与设备/会话绑定。
