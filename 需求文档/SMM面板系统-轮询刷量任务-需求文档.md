# SMM 面板系统 — 轮询刷量任务 需求文档

> 版本：v1.0
> 创建日期：2026-11-04
> 所属系统：youtube-sys / SMM 面板系统
> 前置：`SMM面板系统-需求文档.md`（账号 + 普通刷量任务已上线）

---

## 一、背景与目标

普通刷量任务是一次性下单。而实际运营需要的是「**维持 VPH（每小时播放量）**」的长期自动化：

- 视频新发布 → **首次刷 350~500**（一次性起量）
- 之后 **每小时刷 1~5**（随机），维持 VPH 曲线
- 只在 **每天北京时间 12:00–21:00（可配置）** 刷，其他时段不刷

目标：在任务管理中新增「**轮询刷量任务**」，创建后由后台调度器自动按小时下单，把「首发 + 维持」整条链路自动化，运营只需填一次参数。

---

## 二、关键决策（已拍板）

| # | 议题 | 决策 |
|---|------|------|
| 1 | 轮询次数语义 | **总共刷几次**（跨天直到刷满）；窗口内每小时一次 |
| 2 | 执行时间窗口 | 每天一个时间窗口（起止小时，北京时间），默认 12:00–21:00 |
| 3 | 首次刷量 | **纳入轮询任务**：加「首次刷量人数」字段，创建时先下首单，再开始轮询 |
| 4 | 每批人数 | 1~5 区间内**均匀随机**（random.randint） |
| 5 | 时区 | 窗口按**北京时间**配置；下单时结束时间转**印度时间(IST)** 提交面板 |
| 6 | 下单后不可编辑 | 轮询任务创建后同样不可编辑（只允许停止/删除） |

> 举例：轮询次数=90、窗口 12:00–21:00（每小时一次 = 9 次/天）→ 共跑 10 天。

## 三、功能需求

### 3.1 任务管理页改造
- 「任务管理」内新增 **Tab：普通任务 / 轮询任务**，两种任务分开列表展示。
- 普通任务列表保持现状（去掉编辑按钮后，仅剩 同步 / 删除）。

### 3.2 新建轮询任务（弹窗）
在普通任务参数基础上，新增「是否轮询」开关。**关闭 = 普通任务；打开 = 轮询任务**，打开后出现以下字段：

| 参数 | 类型 | 说明 |
|------|------|------|
| 首次刷量人数 | 数字（选填，默认空） | 350~500；创建时**立即下首单**，不计入轮询次数 |
| 轮询次数 | 数字（必填） | 总共刷几次（每小时一次的维护单，不含首次） |
| 执行时间窗口 | 起止小时（必填） | 北京时间，默认 12:00–21:00，每天在该窗口内每小时刷一次 |
| 每批刷量人数 | 区间 min~max（必填） | 默认 1~5，每次轮询在区间内随机取一个数 |

其余参数（账号、YouTube 链接、关键词、每人奖励 ₹、结束时间等）与普通任务一致。

### 3.3 执行计划预览（日期展示，具体到小时）
- 填好「轮询次数 + 窗口 + 每批人数」后，前端**动态计算并展示**完整执行计划：
  - 每个执行时间点（如 `11-04 12:00、13:00 … 11-13 20:00`，共 90 个）
  - 首次刷量单（如 400 人）单独列在最前
  - 预估总成本 = 首次 + Σ(每批随机人数) × perUser（每批人数按区间均值展示，实际按随机值波动）
- 计划预览为纯前端计算，用于运营确认；实际执行以后端调度为准。

### 3.4 轮询任务列表展示
| 列 | 说明 |
|----|------|
| 任务号 / 账号 / 链接 / 关键词 | 与普通任务一致 |
| 进度 | 已刷 `poll_done` / 总 `poll_total`（+ 首次已刷标记） |
| 下次执行时间 | `next_poll_at`（北京时间，具体到小时） |
| 状态 | 运行中 / 已完成 / 已停止 / 失败 |
| 操作 | 停止、删除、展开查看子下单 |

- **展开子下单**：点击展开，列出该轮询任务已产生的每次实际下单（复用普通任务记录：每单人数、面板任务号、状态、进度）。
- **停止**：将轮询任务标记为「已停止」，调度器不再继续（不撤回已下单）。
- **删除**：仅删本地记录，不撤销面板任务。

## 四、数据模型（新增 `SMMPollTask`，`SMMTask` 加外键）

### SMMPollTask（轮询任务 / 父任务）
| 字段 | 类型 | 说明 |
|------|------|------|
| account | FK(SMMAccount) | 所属账号 |
| youtube_link / key_words | CharField | 链接、关键词 |
| per_user / task_type / plant_form / comment_num | 与 SMMTask 一致 | 下单参数 |
| initial_count | IntegerField(blank,null) | 首次刷量人数，创建时立即下单 |
| poll_total | IntegerField | 轮询总次数 |
| poll_done | IntegerField(default=0) | 已刷次数 |
| batch_min / batch_max | IntegerField | 每批人数区间（1~5） |
| window_start_hour / window_end_hour | IntegerField | 窗口起止小时（北京时间 0-23） |
| next_poll_at | DateTimeField(blank,null) | 下次执行时间（北京时间） |
| status | CharField | running / completed / stopped / failed |
| created_at / updated_at | | |

### SMMTask（子下单，复用现有模型）
- 新增可空外键 `poll_task = FK(SMMPollTask, null=True, blank=True, related_name="children")`。
- 普通任务 `poll_task=null`；轮询产生的每次下单 `poll_task` 指向父任务。

## 五、接口设计

- `GET/POST /api/smm-poll-tasks/`：列表 / 创建（创建时：若有 initial_count 先下首单；再按窗口计算 `next_poll_at`）
- `POST /api/smm-poll-tasks/{id}/stop/`：停止
- `DELETE /api/smm-poll-tasks/{id}/`：删除（仅本地）
- `GET /api/smm-poll-tasks/{id}/`：详情（含 children 子下单列表）
- 调度内部：`POST /publish/sendTask`（复用 `smm.services.send_task`），随机人数 `random.randint(batch_min, batch_max)`

---

## 六、调度器（Celery）

- 复用现有 beat（30s 周期），新增任务 `sync_smm_poll_tasks`（每分钟执行，或并入现有 beat）。
- 逻辑：扫描 `status=running` 且 `poll_done < poll_total` 的轮询任务：
  1. `now = 北京时间`
  2. 若 `now >= next_poll_at` → 立即下单（人数 = 随机 batch_min~batch_max），创建子 SMMTask，`poll_done += 1`
  3. 推进 `next_poll_at` 到下一个窗口内的小时槽（跳过窗口外时段、跨天）
  4. `poll_done >= poll_total` → 状态置 `completed`
- **失败处理**：某单下单失败 → 子 SMMTask 标 failed，`poll_done` 仍 +1（不阻塞后续），任务继续；连续失败 N 次（如 3 次）→ 父任务标 failed 并停。
- **漏发处理**：系统宕机错过某小时 → 不补，直接跳到下一个槽。

## 七、风险与待验证

| 风险 | 说明 | 应对 |
|------|------|------|
| 每批 1~5 人太小 | 面板 UI 最低档 300 人；实测 totalUser=5 可接，1~4 未验证 | 开发时先下 1~2 单测试（花几卢比），确认面板接受并真实刷量 |
| 时区换算 | 窗口北京时间 ↔ 面板 IST（差 2.5h） | 调度按北京时间判断，下单 endTime 按 IST 计算（沿用现有逻辑） |
| 随机成本浮动 | 每批 1~5 随机，总成本浮动 | 列表展示预估成本（按均值），实际以面板为准 |
| 面板接口变更 | 第三方无承诺 | 客户端集中封装，变更只改一处 |

---

## 八、优化点（已采纳）

1. 轮询任务 = **父任务 + 多次子下单**（复用 SMMTask），可展开追溯每次执行。
2. **首次刷量纳入轮询任务**，一个任务覆盖「首发 + 维持」。
3. 前端 **执行计划预览**（具体到小时）+ **成本预估**。
4. 漏发跳过、失败不阻塞 + 连续失败自动停。
